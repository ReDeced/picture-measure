## Быстрый старт

```bash
git clone https://github.com/ReDeced/picture-measure.git
cd picture-measure
cargo test          # убеждаемся, что всё работает
cargo run --release
```

Нужен Rust 1.95 или новее. Ничего доустанавливать не нужно: программа
собирается на `winit` + OpenGL и работает на Windows, macOS и Linux (X11 и
Wayland).

Если что-то не собирается — [откройте issue](https://github.com/ReDeced/picture-measure/issues/new/choose),
разберёмся.

## Как помочь

Порядок по полезности:

1. **Сообщить об ошибке.** Даже мелкий визуальный баг ценен. Используйте шаблон
   «Ошибка» — там есть все нужные поля.
2. **Ответить на вопрос в [Discussions](https://github.com/ReDeced/picture-measure/discussions).**
3. **Улучшить документацию.** Особенно [docs/USER_GUIDE.md](docs/USER_GUIDE.md) —
   если что-то оказалось непонятным, напишите как понятнее.
4. **Добавить тест**, если нашли случай, который стоит зафиксировать.
5. **Сделать фичу.** Перед началом откройте issue с описанием, чтобы можно было
   заранее обсудить подход и не переделывать.

Что программа сознательно **не** делает: не поддерживает многоугольники,
полилинии, произвольные повёрнутые прямоугольники и кривые. Это осознанное
ограничение — формат JSON и модель данных заточены под точки и
прямоугольники. Расширение возможно, но требует миграции формата, поэтому
обсуждается отдельно.

## Работа с ветками

Подробный разбор — в [docs/BRANCHING.md](docs/BRANCHING.md). Коротко:

```text
main        только проверенный код, из него выходят релизы
            └── release/*   подготовка релиза (cherry-pick)

feat/…      новая функциональность      → PR в main
fix/…       исправление ошибки          → PR в main
docs/…      документация                → PR в main
refactor/…  перестройка без изменения поведения → PR в main
chore/…     зависимости, CI, мелочи    → PR в main
hotfix/…    срочное исправление         → PR в main и release/*
```

Правила:

- Ветка нужна для любой работы длиннее одного дня или затрагивающей больше
  трёх файлов. Багфикс на две строки можно отправить прямо в `main`.
- Имя ветки — `тип/что-делаем`, латиницей, через косую черту:
  `feat/square-drag`, `fix/zoom-anchor`, `docs/json-format`.
- Один PR — одна тема. Рефакторинг и новую функцию лучше отправлять отдельно.
- Ветку форкаете от свежего `main`:
  ```bash
  git fetch upstream && git rebase upstream/main
  ```
- Не коммитьте прямо в `main` и не форкайте `main` для своей работы.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <описание в импераливе>

<тело: зачем, а не что>

<подвал: Closes #12, BREAKING CHANGE: …>
```

Типы:

| Тип | Когда |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление ошибки |
| `docs` | документация |
| `test` | тесты |
| `refactor` | перестройка без изменения поведения |
| `perf` | ускорение |
| `style` | форматирование (без логики) |
| `build` | сборка, зависимости |
| `ci` | GitHub Actions |
| `chore` | прочее |

Примеры:

```text
feat(shift): делать прямоугольник квадратом при зажатом Shift
fix(zoom): не терять точку под курсором при масштабировании
docs(json): описать поведение при отсутствующем поле type
test(session): закрыть потерю отпускания кнопки вне окна
```

Одна строка — до 72 символов. Импералив: «делает», а не «делал» или «сделал».

Тело нужно там, где «почему» не очевидно из заголовка. Хороший пример:

```text
fix(release): отменять жест, когда кнопка отпущена вне окна

Бэкенд перестаёт слать события отпускания при потере фокуса окна.
Без проверки состояния кнопки предпросмотр прямоугольника залипал
до перезапуска программы.
```

## Pull request

1. Создайте ветку от `main`, запушьте её в свой форк.
2. Откройте PR в `main`. Описание заполните по шаблону
   [.github/PULL_REQUEST_TEMPLATE.md](.github/PULL_REQUEST_TEMPLATE.md).
3. Дождитесь зелёных галочек в CI (формат, clippy, тесты на трёх ОС, сборка).
4. Ответьте на замечания. Правьте новыми коммитами или
   `git rebase`/`git commit --amend` — историю никто не переписывает при
   обновлении PR.

PR считается готовым к слиянию, если:

- CI зелёный;
- есть тесты на новое поведение;
- документация обновлена, если изменилось поведение или формат файла;
- `CHANGELOG.md` дополнен;
- нет необоснованных переименований и перестановок строк — их проще делать
  отдельным PR.

Мелкие правки в оформлении принять легко, поэтому **переформатируйте весь файл
только тогда, когда правка действительно проектная**. Обычный `cargo fmt` при
этом не трогает чужие строки.

## Проверки перед отправкой

```bash
make check        # fmt --check + clippy + тесты
```

Или по отдельности:

```bash
cargo fmt --all
cargo clippy --all-targets --all-features
cargo test --all-targets
```

Clippy в проекте запускается с `pedantic`. Если линтер ругается на осмысленный
код, добавьте `#[allow(...)]` с пояснением, а не отключайте правило целиком в
`Cargo.toml` — за одним `allow` обычно стоит неверное допущение о коде.

## Качество кода

- **`cargo fmt` не обсуждается.** Настройки — стандартные, спорные места
  решаются комментарием, а не Fight.
- **Публичные элементы документированы.** Включён `missing_docs = "warn"`.
  `# Panics` и `# Errors` обязательны там, где они применимы.
- **Ошибки пользователю — по-русски, без паники.** Ошибки разбора JSON
  возвращаются через `JsonError` с понятным текстом, а не через `unwrap`.
- **Без `unwrap()` в рабочем коде.** В тестах — можно.
- **`unsafe` запрещён** линтером: `#![forbid(unsafe_code)]` включён в
  `Cargo.toml` и не должен обходиться.
- **Никаких новых зависимостей без обсуждения.** egui-экосистема тянет много
  транзитивных зависимостей; каждый новый пакет должен окупаться.

### Где что лежит

| Хочу | Файл |
|---|---|
| Изменить поведение клика, протяжки, Shift | `src/tools.rs` |
| Точки, прямоугольники, имена, подпапки | `src/model.rs` |
| Формат JSON | `src/json_io.rs` |
| Экспорт по подпапкам | `src/split.rs` |
| Зум и панораму | `src/view.rs` |
| Соединить события с правками фигур | `src/session.rs` |
| Отрисовку | `src/gui/` |

Граница проходит по `src/gui/`: **всё, что можно проверить тестом без окна,
живёт в библиотеке.** Если приходится писать логику в `src/gui/`, скорее всего,
её можно вынести в `src/session.rs` и покрыть тестом. Подробнее —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Тесты

```bash
cargo test                                   # всё
cargo test session                           # только про сессию
cargo test --test session_flow               # сквозные сценарии
cargo test -- --nocapture                    # с выводом
```

Тесты не открывают окно и не создают текстуры, поэтому работают на CI без
виртуального дисплея и выполняются за доли секунды.

Что покрыто:

| Уровень | Где | Что |
|---|---|---|
| Модульные | `#[cfg(test)]` в `src/` | геометрия, имена, JSON, автомат жестов, указатель, история |
| Сессионные | `src/session.rs` | события → фигуры → отмена |
| Сквозные | `tests/session_flow.rs` | сценарии пользователя, экспорт, повторное чтение |

### Как писать тест поведения

Для жестов собирайте список кадров: в каждом кадре — события и нажатые кнопки.

```rust
let mut session = Session::new();
let canvas = egui::Rect::from_min_max(egui::pos2(0.0, 0.0), egui::pos2(800.0, 600.0));

// Клик: нажатие, затем отпускание без перемещения.
let down = [egui::Event::PointerButton { pos: pos2(10.0, 10.0), button: PointerButton::Primary, pressed: true, modifiers: Default::default() }];
let up   = [egui::Event::PointerButton { pos: pos2(10.0, 10.0), button: PointerButton::Primary, pressed: false, modifiers: Default::default() }];
session.handle_events(&down, Default::default(), canvas, &[PointerButton::Primary]);
session.handle_events(&up,   Default::default(), canvas, &[]);

assert_eq!(session.set().len(), 1);
assert_eq!(session.set().items()[0].geometry, Geometry::Point(pos2(10.0, 10.0)));
```

Четвёртый аргумент `handle_events` — список кнопок, которые, по мнению бэкенда,
зажаты. Он нужен, чтобы тест повторял поведение настоящего окна и не зависел от
того, как вручную разложены события.

Частые проверки для новых фич:

```rust
// Координаты не зависят от масштаба.
let target = pos2(33.0, 77.0);
user.click(session.screen_of(target));
assert!(session.set().items()[0].geometry.as_point().unwrap().distance(target) < 1e-3);

// Round-trip через JSON ничего не теряет.
let json = json_io::to_string_pretty(set, None, 4).unwrap();
assert_eq!(json_io::from_str(&json).unwrap().items(), set.items());
```

## Документация

| Что изменилось | Где править |
|---|---|
| Поведение программы | `docs/USER_GUIDE.md`, `README.md` |
| Формат JSON | `docs/JSON_FORMAT.md` |
| Структура кода | `docs/ARCHITECTURE.md` |
| Правила разработки | `CONTRIBUTING.md` |
| Что появилось в этой версии | `CHANGELOG.md` |

Формат JSON — контракт с пользователями. Любое изменение полей — это изменение
`version` и заметка в `CHANGELOG.md`. Старые файлы должны продолжать читаться.

## Релизы

Релизы выходят по тегам `v*`:

```bash
git checkout main && git pull
git tag -a v0.2.0 -m "v0.2.0"
git push origin v0.2.0
```

Дальше срабатывает `.github/workflows/release.yml`: он собирает бинарники под
Linux (glibc и musl), Windows и macOS (Intel и Apple Silicon), считает
контрольные суммы и публикует релиз с вложениями.

Подготовка релиза:

1. Обновите `version` в `Cargo.toml`.
2. Перенесите накопленное из `Unreleased` в раздел с датой в `CHANGELOG.md`.
3. Откройте PR с этими изменениями и дождитесь зелёного CI.
4. После слияния поставьте тег.

Ветки `release/*` нужны, только когда в релиз хочется добавить срочные
исправления: в них переносите нужные коммиты через `git cherry-pick`.
